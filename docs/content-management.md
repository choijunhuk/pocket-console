# 게임 준비 상태와 추가 콘텐츠 개선

현재 체크아웃 기준. 구현된 동작과 다음 개발 후보를 구분한다.

## 이번 변경: 기다릴 수 있는 작업만 진행 상태 표시

- Switch·Switch 2의 `준비 중`은 다운로드나 설치 작업이 아니었다. 실행 엔진이 연결되지 않은 상태이므로 `현재 실행 불가 · 엔진 미연결`과 기다려도 실행되지 않는다는 설명으로 바꾼다.
- DS·3DS 실행은 `파일 열기 → 파일 복사 → 파일 검사 → 기존 캐시 확인(있을 때) → 코어 초기화 → 오디오 준비 → 첫 화면 대기 → 실행 중`으로 표시한다.
- 복사와 캐시 검사는 실제 처리 바이트로 백분율과 MiB를 표시한다. 파일 제공자가 전체 크기를 주지 않거나 읽은 크기가 제공된 크기를 넘으면 처리량만 표시한다. 복사 백분율은 전체 부팅 진행률이 아니다.
- 코어가 진행률을 제공하지 않는 단계는 단계명과 경과시간을 표시한다. 15초간 진전이 없으면 오래 걸린다는 안내와 라이브러리에서 취소를 요청하는 경로를 표시한다. 취소는 작업이 응답한 뒤 정리되므로 응답하지 않는 제공자·네이티브 작업의 즉시 종료를 보장하지 않는다. 강제 종료나 임의의 시간 제한으로 저장 데이터를 잃게 하지 않는다.
- 첫 프레임을 플레이어에 전달한 뒤 `실행 중`으로 바꾼다. 오류·종료·화면 파괴 때 로딩 표시 갱신을 중지하고, 회전·전체화면에서는 같은 상태를 이어서 표시한다.

## DLC·업데이트: Ryujinx에서 가져올 흐름

[Ryujinx 계열 설정 가이드](https://docs.ryujinx.app/guides/setup-guide/)는 게임별 **Manage Title Updates**에서 여러 업데이트를 등록하고 적용할 버전 하나를 선택하며, **Manage DLC**에서 추가 콘텐츠를 등록·선택·제거한 뒤 저장하는 흐름을 설명한다. 이 문서는 Ryujinx 파생 프로젝트의 가이드이므로 원본 프로젝트의 현재 배포 상태를 증명하지 않는다.

Pocket Console에는 다음 흐름이 적합하다. 아래는 제안이며 현재 설치 기능이 아니다.

1. 게임 메뉴에서 `업데이트·DLC 관리`를 연다. 업데이트와 DLC를 본편 게임 목록에 별도 게임처럼 추가하지 않는다.
2. 파일 선택 후 코어에서 콘텐츠 종류·게임 ID·지역/버전 조건을 확인한다. 이름이나 `.nsp`/`.cia` 확장자만으로 본편과 연결하지 않는다. 일치하지 않으면 이유를 보여주고 기존 적용 상태를 유지한다.
3. 업데이트는 `본편 버전` 또는 등록된 버전 하나를 선택한다. DLC는 개별 활성화·비활성화와 적용 상태를 표시한다. 실제 지원 범위는 코어별로 정한다.
4. 적용 시 복사·검증·설치 상태와 진행률, 필요한 여유 공간, 취소·오류를 표시한다. 설치가 성공한 뒤에만 적용 상태를 저장한다. 실패·취소 시 기존 설치와 세이브를 보존한다.
5. `등록 해제`, `설치 데이터 삭제`, `원본 삭제`를 구분한다. 기본 동작은 원본과 세이브를 보존한다. 실행 중에는 변경을 막고 종료 후 적용한다.
6. 앱 재실행 후 코어에서 실제 적용 상태를 확인한다. 파일 권한이 해제되면 재선택을 안내하며 중복 등록은 콘텐츠 ID와 버전으로 판별한다.

### 현재 막혀 있는 부분

- DS의 현재 카트리지 실행 경로에는 이 방식의 콘텐츠 설치 API가 없다.
- 3DS는 `third_party/azahar.lock.json`의 Azahar 2126.2를 사용한다. 현재 `ThreeDsNative`는 열기·프레임·종료만 노출하며 설치·콘텐츠 조회 API가 없다. `ThreeDsRomCache`와 파일 분류는 CIA를 받지 않는다.
- 고정 소스의 [AM 설치 함수](https://github.com/azahar-emu/azahar/blob/219d743a1e698101fe1ab8bef43e6563126c3c27/src/core/hle/service/am/am.h#L418-L432)에는 `InstallCIA`, `CheckCIAToInstall`, `GetCIAInfos`가 있다. 현재 ARM64 바이너리에도 이 C++ 심볼이 존재한다. 그러나 [libretro 진입점](https://github.com/azahar-emu/azahar/blob/219d743a1e698101fe1ab8bef43e6563126c3c27/src/citra_libretro/citra_libretro.cpp#L503-L552)은 설치 API를 제공하지 않는다. 별도 Android 앱의 JNI처럼 앱에서 안전하게 호출하는 연결, 본편·콘텐츠 ID 검증, 같은 사용자 디렉터리의 단일 작업 소유권, 실패 시 설치·세이브 보존 검증이 필요하다. 함수가 바이너리에 있다는 사실만으로 DLC 설치 지원을 선언하지 않는다.
- [Libretro Azahar 문서](https://docs.libretro.com/library/azahar/)의 실행 파일 목록에도 CIA가 없다. [Azahar 릴리스 노트](https://github.com/Azahar-Emu/Azahar/releases)는 업데이트·DLC용 ROM Bundle을 2127.0부터 안내한다. 일반 Azahar의 Bundle 지원이 현재 고정된 libretro 빌드의 지원을 증명하지는 않는다. 버전 업그레이드만으로 설치 기능이 생긴다고 가정하면 안 된다.
- Switch·Switch 2의 실행 엔진은 이 체크아웃의 앱과 연결되지 않았다. 먼저 해당 코어의 콘텐츠 조회·검증·적용 API와 실제 실행을 연결해야 한다.

따라서 이번에는 적용되지 않는 파일을 `DLC 설치 완료`로 저장하는 기능을 만들지 않는다. 다음 구현의 완료 조건은 독자 작성 테스트 콘텐츠로 본편 실행 → 콘텐츠 적용 확인 → 비활성화 → 재실행 유지 → 잘못된 게임 ID 거부 → 취소/공간 부족 후 기존 설치·세이브 보존까지 확인하는 것이다.

## 추가 개선 후보와 우선순위

| 우선순위 | 후보 | 현재 근거와 완료 조건 |
| --- | --- | --- |
| 높음 | 세이브 내보내기·가져오기 | 저장은 앱 내부에 있고 내보내기 UI가 없다. 재설치·기기 교체 전에 문서 선택기로 백업하고, 게임을 종료한 뒤 형식 확인·기존 데이터 백업을 거쳐 복원한다. DS 해시별 저장과 3DS 사용자 디렉터리 구조를 보존해야 한다. |
| 높음 | 캐시 사용량·선택 삭제 | 캐시가 콘텐츠 해시별로 쌓이며 사용자용 정리 UI가 없다. 종류·용량·재생성 가능 여부를 먼저 보여주고 ROM 캐시만 선택 삭제한다. `ds-saves`와 `three-ds-user`는 정리 대상에서 제외한다. |
| 높음 | 파일 권한 복구 | 보관함의 실행 불가 경로에는 접근 복구 안내가 있으나 DS·3DS 플레이어의 실패 후 재선택은 별도 동선이다. 원래 항목과 세이브 연결을 유지하며 파일을 다시 연결하는 기능이 필요하다. |
| 중간 | 게임별 실행 정보 | 기종·파일 크기·적용 업데이트·활성 DLC·최근 오류를 게임 메뉴에서 확인한다. 단순 URI가 아닌 코어의 게임 ID가 필요한 콘텐츠는 코어 확인 결과를 사용한다. |
| 중간 | 외부 컨트롤러 | 현재 플레이어는 화면 버튼 중심이다. 키·스틱 매핑, 기기 분리 시 눌림 해제, 화면 버튼 숨김과 함께 검증한다. |
| 이후 | 성능 진단 | 실제 프레임 시간·오디오 누락·지속 발열을 측정한 뒤 표시한다. `실행 중`만으로 성능이나 게임 호환성을 보장하지 않는다. |

### 후속 로컬 빌드

Gradle의 소켓 제한을 우회하기 위해 Gradle을 사용하지 않는 로컬 테스트 빌드를 만들었다. `javac → D8 → aapt2 → NDK → zipalign → apksigner`를 사용한다. DS 코어와 두 네이티브 연결 코드는 두 ABI 모두 새로 빌드했으며, Azahar 바이너리는 고정 manifest·SHA-256 확인 후 재사용하고 패키징용 사본에서 디버그 심볼을 제거했다. Gradle/CI 빌드 성공을 뜻하지 않는다.

- `.cache/preparation-apk/PocketConsole-progress-test.apk`: 수정된 실제 앱 소스와 리소스를 담은 로컬 디버그 APK. 원래 앱 ID를 사용하며 정식 배포 서명과 다르다. 기존 앱을 삭제해서 설치하는 방식은 세이브를 잃게 하므로 사용하지 않는다.
- `.cache/preparation-apk/PocketConsole-progress-qa.apk`: 별도 앱 ID `dev.pocketconsole.progressqa`를 쓰는 QA APK. 원본 앱과 데이터를 공유하지 않는다. 크기를 아는 제공자·모르는 제공자·정체 상태용 느린 파일 제공자와 독자 작성 DS 홈브루를 테스트 도구로 포함한다. 제품 기능 추가가 아니다.
- 서명(v2/v3), 실제 진행 상태 클래스의 DEX 포함, 패키지·버전·min/target SDK·두 ABI, ZIP/ELF 16KB 정렬 검사를 통과했다. 입력 소스와 산출물 해시는 `.cache/preparation-apk/build-provenance.json`과 각 APK 옆의 `.sha256`에 기록한다.
- 모바일 도구의 로컬 Android 16 ARM64·16KB 에뮬레이터 `PocketConsole_Display_QA`에 QA APK 설치 성공을 확인했다. 앱 실행 요청은 승인 필요/승인 정책 `never`로 거절되었다. 따라서 실제 앱 실행·진행률 화면·게임 부팅·스크린샷 검증은 **NOT_RUN**이다.
- 이전 제한 세션에서는 GitHub 검증용 Git tree 생성도 같은 승인 정책으로 차단되었다. 당시에는 코드 업로드·CI 실행·새 배포를 하지 못했다.

### 권한 변경 후 게시 상태 (2026-11-17)

Full access 적용 후 CLI의 GitHub 원격 조회가 정상화되었다. 로딩 진행 상태 코드와 테스트, README, `.gitignore`는 `feat/3ds-emulation`의 `22d7e0c`에 커밋되어 있으며 로컬과 GitHub의 커밋이 일치한다. 이 문서와 `.ignore`는 누락된 파일로 확인되어 별도로 추가한다. 이 확인은 새 APK 배포나 Android 실행 검증을 뜻하지 않는다.

변경 파일은 `MainActivity.java`, `DsPlayerActivity.java`, `ThreeDsPlayerActivity.java`, 두 `*RomCache.java`, 신규 `PreparationProgress.java`, 대응하는 세 Java 모델 테스트, 두 모델 테스트 스크립트와 README/이 문서다. 두 기종의 진행 상태 계산을 하나로 공유하며 새 의존성은 추가하지 않는다. melonDS 서브모듈의 로컬 수정은 `scripts/prepare-core.py`가 적용한 고정 패치이며 별도 서브모듈 커밋으로 추가하지 않는다.
